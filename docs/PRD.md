## 1. 产品定位与核心理念

### 1.1 一句话定位
**BodySeek（工程身份 Vela）是建立在 Apple 健康之上的个人身体状态仪表与 AI 分析助手：先用五个独立分数和个人基线量化当下状态，再由 Agent 解释变化、支持追问，并把必要的调整组织成用户拥有的日常计划。**

### 1.2 核心原则
> **核心原则**：让用户看见“这不是意志力问题，而是身体确实发生了可观察的变化”；分数负责建立直觉，Agent 负责解释和行动，不用冗长文案替算法找补。

### 1.3 核心价值层级（不可颠倒）
1. **看见身体数据**：把 Apple Health / Apple Watch 分散的体征与信号完整汇聚、清晰呈现；
2. **理解当前状态与长期变化**：通过 Recovery、Sleep、Strain、Physiological Stress、Energy 五条独立时间序列，以及 7天 / 30天 / 6个月 / 3年个人基线，理解身体稳态与偏离；
3. **由 Agent 解释原因、联系不同信号**：AI 分析师提供跨系统关联观察与候选影响因素假设，探讨体征、压力、睡眠与行为之间的联系；
4. **在需要时给出训练与生活建议**：将对身体的理解落地为克制、明确、符合生理负荷边界的行动方案。

## 2. 目标用户与使用场景

### 2.1 Primary User（核心用户）
- **定义**：拥有约 1100 天真实 Apple 健康数据积累、佩戴 Apple Watch、日常从事高强度脑力/科研工作、保持力量训练习惯且有长期健康减脂目标的产品作者本人。
- **阶段原则**：在个人 Daily Driver 阶段，真实作者的连续使用体验与真实反馈是产品最高优先级的需求输入；不引入假设性大众用户的妥协设计。

### 2.2 真实使用习惯契约
- **手表主导记录**：Apple Watch 负责全天体征监控、心率采集以及运动现场记录；用户在训练过程中不操作手机记组、记动作；
- **手机主导决策与解释**：iPhone 负责同步数据、计算身体状态、呈现多尺度趋势、由 AI 深度推理原因并给出行动建议；
- **长线柔性轮转**：力量训练按肌群轮转推进（如背、胸、肩、腿、手臂/核心），不强制绑定星期几；
- **保护健康节律**：当短期减脂目标、训练打卡与身体恢复产生冲突时，Vela 始终优先保护并恢复可持续的健康节律。

## 3. 北极星指标：Trusted Health Brief Day

**`Trusted Health Brief Day`（可信身体简报日）** 是 Vela 的唯一北极星标准：
> **评判标准**：一天中，Vela 是否可靠地回答了用户的三个根本问题：
> 1. **我现在身体总体怎么样？**（How am I overall right now?）
> 2. **最近发生了什么值得注意的变化？**（What has changed recently?）
> 3. **我是否需要采取行动？**（Do I need to take action?）

- **价值均等原则**：身体状态稳定、无需改变计划的一天，与触发减量或调整的一天具有同等完整的价值；
- **非目标指标**：不以打开次数、停留时长、聊天消息数或单纯刷高健康分数作为北极星。

```text
    ↓

    ↓

    ↓
生成 Personal Health Brief（全局权威认知对象）
    ↓
┌───────────────┬───────────────┬───────────────┬───────────────┐
│     Today     │    Trends     │     Plan      │     Coach     │

    ↓
后续真实数据更新与主观反馈校准模型判断
```

## 5. 一级信息架构（四大工作区）

Vela 采用清晰的 4-Tab 导航结构，Settings 收敛为系统级二级界面：

```text
Vela App
├── Tab 1: Today（五分身体状态）
├── Tab 2: Trends（多尺度趋势与指标详情）
├── Tab 3: Plan（今日健康行动与安排）
└── Tab 4: Coach（AI 分析、追问与记忆）
    └── Settings（设置、数据覆盖、权限与控制，右上角/二级入口）
```

### 5.1 Tab 1 · Today（五分身体状态）
- **核心定位**：用最短路径回答“我现在怎么样？是否与我的感觉一致？”；
- **首屏元素**：
  - **固定 3+2 状态仪表**：Recovery、Sleep、Strain 固定为第一视觉层级并使用圆环；Physiological Stress 以当前值和紧凑趋势线呈现，Energy 以身体电量/余量槽呈现；不生成总分；
  - **主卡内 Agent 指导**：紧跟三项主圆环，只保留一句指导。有恢复分时引用「恢复 82」这样的整数，不用百分号，也不从单一恢复阈值宣布各项体征都好。事实不变时文案保持稳定，离线时使用本地表达，点击后携带今日状态进入 Coach 追问；
  - **睡眠圆环**：只使用睡眠分。睡眠时长是独立信号，不点亮睡眠分圆环；
  - **偏离与缺失**：Personal Baseline Deviation 只用克制标记表达“对你而言不寻常”；缺失值显示 `--`，不伪装正常；
  - **初始基线形成**：首次连接后的前 7 个有效观察日，只在五分区域显示一行紧凑进度；各指标仍按自己的有效样本独立启用，达到初始门槛后进度自动退出，不能把“首周完成”描述成长期基线已经稳定；
  - **Lived State 校准**：看完分数后可选“符合感受 / 感觉更差 / 感觉更好 / 不确定”，并可继续追问；
  - **计划摘要**：展示今日默认 Daily Operating Plan 的下一项健康行动，进入 Plan 后可编辑。

仪表表达当前状态而非目标完成度。Recovery、Sleep 越高通常越有利；Physiological Stress 越高越需关注；Strain 只表示负荷量；Energy 表示会随恢复与消耗而变化的可用余量。主界面不常驻置信度辩解、贡献因子列表或长解释，这些进入指标详情与辅助功能描述。

### 5.2 Tab 2 · Trends（多尺度趋势与指标详情）
- **核心定位**：回答“最近身体发生了什么长期变化？”；
- **首屏元素**：
  - **多尺度时间维度**：支持 7 天、30 天、6 个月、3 年的历史基线对比；取数跟随当前所选窗口，不总是预取三年；
  - **五分时间序列优先**：首屏固定展示 Recovery Score、Sleep Score、Strain、Physiological Stress、Energy 五条时间序列；Sleep Score 与原始睡眠时长必须独立建模，不得混用；
  - **基线偏离标记**：直观展示指标是处于稳态区间，还是显著偏离个人历史基线；
  - **二级详情页**：提供高精细度历史图表、内日分布与统计分位数。
  - **证据下钻**：先按五个分数组织，HRV、静息心率、睡眠时长等原始 Health Signals 默认收进“更多健康指标”，再进入贡献因子、算法版本与方法页。

### 5.3 Tab 3 · Plan（今日健康行动与安排）
- **核心定位**：回答“基于今天的状态，我准备如何安排健康相关行动？”；
- **首屏元素**：
  - 每日自动存在一个本地可用计划，包含 1 个主要行动与最多 2 个辅助行动；
  - 计划只覆盖训练、运动、饮食节律、压力恢复与睡眠，不接管通用日历或待办；
  - 用户可直接编辑、删除、改期或替换行动，拥有最终决定权；
  - Agent 后续提出实质变更时展示完整候选行动；当前正式计划保持可见，用户明确确认后才生效；
  - 已保存的正式行动序列在身体状态变化时保持不动。Plan 出示候选，用户确认后才替换。用户完成、编辑或排期同样不得被后台刷新静默覆盖。

### 5.4 Tab 4 · Coach（AI 分析、追问与记忆）
- **核心定位**：回答“为什么会这样？还需要追问什么？Vela 应记住什么？”；
- **首屏元素**：
  - 从 Today 的分数、偏离或短句带上下文进入追问，也支持开放式问题；
  - 基于 Agent Fact Snapshot 与按需时间序列工具解释关联，不读取或上传全量原始 HealthKit 样本；
  - 集中呈现对话历史、结构化 artifacts、已确认记忆与待确认 Memory Proposals；
  - 训练作为 Plan 的下游能力：运动现场由 Apple Watch / 系统执行，Vela 只负责事前边界与事后观察。

### 5.5 Settings（设置、权限与数据控制）
- **组织方式**：作为二级页面由各 Tab 顶部或个人入口拉起，不占用一级 Tab；
- **功能职责**：Apple Health 权限授权、数据覆盖度检查、数据源同步控制、AI Provider / API Key 配置、数据导出与删除；
- **信任中心**：必须先展示用户所有权，而不是先展示技术日志：身体分数在本机计算、联网 Agent 逐类授权、Agent 修改计划或长期记忆前由用户确认、本地数据可导出或删除；Agent 运行时间、结果与工具调用作为下游审计记录。

### 5.6 首次使用（身体状态与信任）
- **固定顺序**：身体状态价值 → Agent 权限与用户所有权 → Apple 健康只读授权；首次启动不得先要求填写训练问卷或配置模型；
- **首屏预演**：用与 Today 一致的 Recovery / Sleep / Strain 三圆环，以及 Physiological Stress 趋势仪表、Energy 余量槽解释五项独立分数，不展示总分；示例数据必须明确标记为示例；
- **默认计划**：完成首次使用后本地建立可编辑的默认计划，用户不需要先完成训练偏好问卷；后续可在 Plan 与设置中自主调整；
- **非授权墙**：Apple 健康可以稍后连接。跳过时如实保留 Data Coverage 缺失状态，不伪造分数，也不阻断本地功能；
- **首周反馈**：连接后立即呈现已有分数；个人基线尚在形成时显示 `初始基线 · n/7 天`，而不是用空白页或长篇说明阻断使用；
- **权限分离**：Apple 健康读取权限与联网 Agent 出站数据授权是两套独立控制。Vela 不写入或修改 Apple 健康原始记录；联网 Agent 只获得用户逐类允许且与当前问题相关的上下文。

## 6. 数据与 AI 交互边界

### 6.1 本地规则与 AI 的职责划分
| 领域 | 本地计算引擎（Local Engine） | AI Agent / Cloud LLM |
| :--- | :--- | :--- |
| **健康评分** | 唯一负责（0–100 分数由本地确定性算法计算） | **禁止重算**；仅读取并引用已有分数 |
| **偏离与安全边界** | 唯一负责 Personal Baseline Deviation 与经过验证的绝对安全规则，并严格区分二者 | 不得把“对你不寻常”转述成疾病或危险；自然表达本地约束 |
| **原因解释与关联** | 计算统计学相关性与基线偏离 | 负责自然语言推理，联系睡眠、压力、行为提出候选假设 |
| **每日计划** | 每天生成本地默认计划、维护正式记录与安全约束 | 组织和自然表达计划；后续实质变更生成可审查 diff，**必须经用户确认** |

### 6.2 语言与归因规范
- **禁止断言生理因果**：AI 可以提出“候选影响因素”（Candidate Drivers）和“观察到的关联”（Observed Correlations），但严禁向用户宣称确定的因果结论；
- **缺失数据客观表达**：未采集或同步的数据显示 `--` 或说明数据缺失，严禁伪造健康数据或将未填写自评默认为“无压力/无酸痛”。

## 7. 产品非目标（Non-Goals）

1. **不做泛健康数据罗盘**：不堆砌无解释力的生硬数字与复杂图表；
2. **不做手动记组工具**：不强迫用户在 iPhone 上记录动作、组数、重量与组间休息（交给 Apple Watch 自动采集）；
3. **不做强制热量记账与惩罚性补偿**：不推崇用惩罚性有氧或极端节食去“抵消”暴饮暴食；
4. **不做医疗诊断与虚假健康年龄**：不提供虚假的“生物学年龄预测”作为营销噱头，不提供严肃医疗诊断；
5. **不脱离用户确认静默改写计划**：AI 的任何调整方案均须经用户 Explicit Confirmation 才能生效。
6. **不做总健康分或固定身体公式**：五个分数保持独立；Body State 是不确定的解释对象，不被包装成第六个分数。

## 8. 本版已固定

本版就是现行软件。下面这些事实以当前源码为准，不再把原型门禁或旧信息架构写成未完成规格：

- 主屏幕名称是 BodySeek。工程 bundle 仍是 `com.sunweizhou.Vela4`。手表目标的显示名仍是 Vela。
- 四个一级表面是 Today / Trends / Plan / Coach。Today 仍是 3+2：恢复、睡眠、负荷为圆环，压力与能量为次级。没有总健康分，也没有健康年龄或生物年龄。
- 部署底线是 iOS 17 / watchOS 10，见 ADR 0017。
- 五项分数各自独立。缺失数据显示 `--`，不写成 0，也不伪造成一个正常值。
- 原始 HealthKit 采样不上云。联网 Agent 只接收裁剪后的结构化上下文。
