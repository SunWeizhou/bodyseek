# Coach 数据治理与持续跟进设计

> 状态：后续设计参考，待按场景拆分工单。
> 本文整合 Ontology Agent OS 提案中可复用的对象关系、餐食转换、复盘与跨页面投影设计，并按修订提案校正边界。
> 产品决定见 [Coach 顶层设计](coach-agent.md)，近期开发从 [实施工单](coach-agent-implementation.md) 开始，已上线能力以 [现行指南](../AI_AGENT_SPEC.md) 和生产代码为准。

## 1. 沿现有数据链扩展 Ontology

HealthKit 负责设备采样和同步，BodySeekCore 持有共享含义和确定性规则，GRDB 持久化本地业务记录，ReadModel 向页面和 Coach 投影同一份事实。Coach 负责把用户意图组织成证据查询、候选操作或跟进任务。授权、核验、计算和提交由对应的本地入口承担。用现有对象 ID 建立需要的关联，随每个完整流程扩展类型化合同。

| 关系 | 需要验证的业务含义 |
| --- | --- |
| 训练记录与标注 | 标注指向实际训练。Watch 回流和手动记录只有在同一来源命名空间 ID 相同、已有确认关联或用户明确选择时自动关联。时间相近的候选需要确认。保留来源，统计只计关联后的实际训练。 |
| 目标、日计划与实际执行 | 目标确定衡量标准和时间范围。日计划可服务于多个目标或独立存在。执行依据是有效训练、打卡等实际记录。分别显示已采纳计划、已完成行动、未记录的执行。 |
| 餐食、睡眠与规则 | 进食记录只有在时间精度满足查询条件时才可出现在睡前窗口。时间相邻表示共现，解释保留不确定性。 |
| 记忆、规则、发现与阶段优先级 | 用户确认的偏好和限时约束可以影响建议。个人规则负责分类，观察到的关联带自己的证据及有效期，经确认的规律可进入对应记忆层。 |
| 跟进任务与复盘 | 一项任务引用其关注的目标、规则或问题及观察窗。完成时的复盘引用所用版本、证据和覆盖状态。任务后续修改和事实订正各有历史。 |

同一实体用稳定 ID，明确记录来源和关联依据。事实的发生时间、App 获知时间和归属生理日各有用途。过去某日的统计按该日适用的数据解释，过去某次建议按当时已经可见的证据解释。切日沿用 04:00 生理日，跨夜关联使用实际发生时刻或有精度标记的时间段。

## 2. 餐食复用与数据订正

- **一套草稿转换，两条用户入口。** 营养页和 Coach 共享已有餐食解析、食物库换算及估算校验。抽取可共享的转换时，同时保留营养页的手动份量与逐项覆盖、原条目 ID、未知值留空、粗估区间及逐项来源。沿用已核对的优先级，手工值优先、食物库换算其次、AI 粗估补缺。Coach 提案复用现有营养保存方式和对象标识。
- **进食发生时间独立于保存时间。** `recorded_at` 保留录入或保存语义。补餐时能力时可使用可空时刻或区间，附时区和精度。历史条目的未知时间继续留空。日结状态、营养字段完整度、餐时可用性各自计算。比较晚饮咖啡的样例应包括明确 16:00、仅说「下午」、「有咖啡但时间未知」和跨午夜，按各自精度入组。
- **订正可解释。** 订正后当前统计读最新事实。保留中的旧复盘应可显示其采用的目标、规则和算法版本、观测日期、生成时的数据截止点和可追溯的证据引用。复盘所需的最小证据以记录 ID 和版本、或允许保留的必要读数为限。数据迟到或被纠正后，提示它改变了哪项结论。删除和数据保留设置同时约束历史复盘和审计内容。

## 3. 目标版本、记忆与个人规则

- **目标按日期解析。** 使用同一个目标选择函数供今日、健身、Coach 和复盘调用。定义同一目标的身份、适用周期、生效日期及显式替代关系。未来生效的版本到日期后才适用。限时覆盖失效后恢复该日期仍有效的基础目标，期间的新指令按自己的生效范围解析。同一日期有多个未明确优先的候选时向用户确认。保存方案应可回答「当时用户要求什么」和「现在如何算这一周」。
- **进度沿用实际记录。** 明确周开始日、时区、训练合格条件、跨日归属与合并规则。周中改目标保留此前实际训练，进度的目标值和实际数量分别取证。阶段优先级约束 Coach 给出的选择，不把先前计划自动算作执行。
- **记忆可纠正，个人规则可版本化。** 只加载相关且仍有效的事实、偏好和过去决定，保留用户可查看的来源、适用期及停用入口。「赶工夜」之类个人规则需定义观测时点、数据来源、条件、缺测行为和生效范围。规则存在明确的版本，停用后停止用于新分类。旧报告仍可解释当时用了哪版规则。正式评分和推断各沿用自己的版本。
- **验收反例。** 未来目标不能提前出现，两周临时安排到期后不能使原目标消失。目标变更不改变历史训练次数。规则依赖的起床时间缺失时归为未知。Coach 对一串晚练和晚睡记录可以提出观察，经用户确认才沉淀为相应的长期记忆。

## 4. 写入、跨页面一致性与跟进

- **授权来源单独核验。** 按 [顶层授权规则](coach-agent.md#3-对话操作与授权) 区分明确的用户编辑意图与 Coach 建议。把授权绑定本轮用户动作、确切对象、范围及拟写变更。历史对话、工具结果和模型输出仅作上下文或候选。幂等标识只关联重试，提交时重新读取对象、验权并检测变更。回执跟随持久化结果，撤销和自动写入同批上线。
- **多步按依赖处理。** 例如「把这周目标改成两次，周日跟我复盘这次调整」，复盘引用已提交的目标版本。相互依赖的改动一并确认，一并提交或等待。独立操作各有回执。提交失败时给出可重试状态。撤销检测确认后新写入及删除，避免把已删训练重新带回。
- **先走现有提交和读取链。** 扩展现有 ReadModel、TCA 刷新和审计入口。需要刷新时，各页以同一份提交后的对象或版本为准，丢失通知、旧异步响应、离线恢复或重新打开 App 后仍可回到已持久化的事实。只有在实际流程验证显示现有机制不够时，再评估观察订阅或通用事件分发。
- **跟进有三条时间线。** 记录观察窗口、何时检查，以及何时和通过哪个入口反馈。用户改提醒时刻时保留观察范围，除非明确一起修改。区分等待取证、需要用户判断、结果可查看、已完成和已停止。到期但尚未生成结果时显示「待复盘」。App 打开后补检查到期任务，持久化去重。已停止任务不继续生成，模型不可用时可恢复重试。通知授权绑定任务，修改或停止任务时同步其通知。
- **晚到事实有验收路径。** 周日复盘按两次训练交付。周一 Watch 补入第三次后，本周历史进度显示三次，旧复盘提示其生成时只收到两次。用户可以查看变化或请求一次新复盘。两次复盘有各自的证据和交付状态。

## 5. 后续工单的拆分依据

完成近期两张工单后，按以下完整场景拆分。具体表、工具名和界面位置在开工时根据已验证的现有入口决定。

| 场景 | 优先复用 | 验收重点 |
| --- | --- | --- |
| Coach 一段话记全天饮食 | 现有营养草稿、食物库和确认保存链 | 同一份输入经两条入口产生一致餐次、份量、逐项估算和缺项。用户能校正并在对应日期看到结果。 |
| 通过聊天修改一个阶段目标 | 已验证的本地授权、回执与撤销机制，共享目标读取 | 「这周三次改两次」与「是不是该少练」正确分流。今日、健身、Coach 的目标版本一致，旧训练保留。 |
| 两周观察任务及复盘 | 已验证的跨天证据与复盘对象 | 可查询进展、停止、改提醒或观察范围，处理数据不足、模型不可用、重复触发与 Watch 晚同步。先在 App 内交付，再按明确授权验证通知。 |

任一阶段的上线能力按路由和真实入口回写现行开发指南。候选技术设计通过迁移、失败路径、页面一致性和设备流程验证后再固化。
