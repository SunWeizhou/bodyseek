## 工单 1 · 用正确的证据解释近 7 天恢复变化

用户问「这周恢复为什么下降」时，先核对是否有下降及其参照，再给出有证据的候选解释和数据缺口。一次有界查询对齐恢复、睡眠、训练、体感和饮食。该工单沿用现有 GRDB v4、`bodyseek-evidence-v1`、本地评分与 ReadModel。

### 日期、覆盖和查询合同

- 从请求捕获的参考时刻与本地时区解析 `endDayKey`，使用 04:00 生理日。目标窗为 `[endDay - 6, endDay]`，此前对照窗为 `[endDay - 34, endDay - 7]`，零重叠。无效或未来日期返回明确错误。当天尚未结束时在结果中标明。逐日数组固定 7 个日期，早于已同步范围的日期保留缺失。
- 覆盖率按每项指标、每个窗口报告，有效观测天数除以 7 或 28 个生理日。独立列出四态天数。中位数、IQR 等统计另报样本数。真实零按该指标现有观测合同处理，该零确实代表有效观测时计入覆盖及统计，缺失和排除保持原状。基线有效样本不足 7 天时返回证据不足，7 天是可描述比较的最低覆盖门槛，显著性结论需另有依据。
- 将「前一段 28 日的固定参照」与评分引擎或趋势图现有逐日滚动基线明确区分。与 UI 对拍时核对同日原始输出，固定对照统计用同一窗口的独立夹具验算。
- 在 [CoachToolRegistry](../../BodySeekKit/Sources/BodySeekAgent/CoachToolRegistry.swift) 注册 `get_weekly_recovery_evidence`，在 [CoachAIClient](../../BodySeekKit/Sources/BodySeekAgent/CoachAIClient.swift) 给 Apple Foundation Models 增加共享适配。两路调用同一份确定性查询逻辑。载荷包括目标和对照日期、按指标统计与覆盖、逐日观测、同日所有已去重且未删训练的必要字段、体感和饮食摘要。控制各类记录和长度的上限，必要时明确标注截断。使用现有 UUID、训练来源与记录归属，沿用现有隐私预览。
- 饮食摘要分别表达日结状态、所查营养字段的完整度和进食时间精度。保留热量区间、已记录小计、估算来源及缺项。既有 `recorded_at` 是录入或保存时间。此阶段的历史进食时刻保持未知，咖啡名称可作为观察线索。
- 每个核心数字关联日期或统计窗口、指标、单位、估算状态与本轮证据键。增量增强 [NumericProvenanceVerifier](../../BodySeekKit/Sources/BodySeekAgent/NumericProvenanceVerifier.swift)，或用类型化证据直接生成依据内容。新增流程中错指标、错日期、错单位和拿日期数字冒充读数均判未核实，旧版数字白名单继续支持旧工具的兼容表达。

### 完成条件

1. 固定数据夹具覆盖 04:00 切日、当前日部分数据、无效日期、对照窗不重叠、稀疏历史和有效零。28 天含 3 天缺失和 2 天排除时，有效观测覆盖为 23/28，统计样本为 23。
2. 同日 09:00 力量及 20:00 羽毛球各被计入一次。缺睡眠数据时如实标出，时间不明的咖啡保留为未确认线索。给出「写成另一天同值」「HRV 与恢复分互换」「单位写错」的否定夹具。
3. 用相同恢复提问验证云端、端侧适配及不可用路径。脚本验证一轮跨域取证可完成，分别记录在线模型的实际调用与回复。iPhone 验收核对日期、趋势读数、解释范围和缺失提示。

## 工单 2 · 唯一 Watch 训练标注、跨页刷新与撤销

先跑通「给昨晚那次 Watch 训练补上腿训标注」。沿用当前用户确认卡和 [ActionExecutor](../../BodySeekKit/Sources/BodySeekStore/ActionExecutor.swift) 审计。候选选择、提交回执、幂等、可见刷新和可撤销在同一工单上线。聊天指令直接写入、组合操作、目标版本和持续任务按顶层设计后续交付。

### 定位与提交

- 云端与 Apple Foundation Models 共用同一个日期与候选解析器。捕获发送时刻和时区。按生理日解析「今天」「昨天」「前天」，对「昨晚」「昨夜」「前晚」用明确的本地夜间窗口处理，包括午夜至 04:00 的训练，测试在凌晨提问的情况。无日期且无选定 UUID 时，用已有记录查询近 72 小时待复盘力量训练，唯一候选仍展示确认。
- 明确日期或 UUID 时尊重该范围。无候选就呈现缺失，多候选就让用户按开始时间和训练类型选，日期与 UUID 冲突则请求澄清。候选排除已删除 UUID、后于参考时刻结束的训练。确认卡绑定唯一 UUID 和展示时的相关记录状态，提交时重新校验。两路模型只生成可确认的候选或提案。
- 复用当前 `CoachFeature` 以消息 ID 创建标注提案、`ActionExecutor` 以该 ID 查审计的幂等合同。区分已提交、已拒绝、已撤销和输入冲突。同一操作重试返回原决策和当前状态，新一轮标注使用新操作 ID。审计和 UI 的确认回执以实际写入为准。
- 从 `v4_healthkit_workout_deletions` 增量迁移，新增版本化撤销快照字段和原操作到撤销记录的关联，保持旧审计可读及 `decided_at` 为 DOUBLE。迁移后同步更新稳定标识测试。只在证明现有提案 ID 无法满足要求时扩展幂等索引。
- 单事务内重查训练和删除记录，校验确认时的记录状态，捕获修改前后该次操作影响的训练标注、肌群负荷与复盘状态，写入审计。使用已有 `WorkoutReviewState.annotated` 合同。撤销按原操作 ID 定位，使用稳定顺序比较存储状态，原子恢复被这次操作改动的内容并留撤销审计。明确区分已撤销、记录后续改动、已删除及旧审计没有快照的情况。后续改动或删除发生时提示冲突，保留当前记录。复用现有标注行及排序语义，避免只恢复一个摘要却改变历史标注的选取结果。

### 刷新与完成条件

- 沿 [AppFeature](../../BodySeekKit/Sources/BodySeekFeatures/Reducers/AppFeature.swift) 的 `watchWorkoutsLoaded` / `reviewPersisted` 路径核对现有刷新。提交和撤销共用同一权威读取及子页面刷新，沿用删除标记过滤和今日建议、Coach 上下文更新逻辑。并发刷新时以最新已提交状态为准。重开 App 后，审计能恢复已保存或已撤销的回执。
- 储存测试从带旧审计和删除标记的真实 v4 结构升级，覆盖确认重试、事务失败、无标注与已有标注两种恢复、再次撤销、拒绝后的重试、提案展示后同步删除、后续手改冲突。Deleted HealthKit 训练在重试、撤销和刷新后均不重现。
- TCA 与 SwiftUI 回归验证：确认唯一候选 → 健身页标注和肌群负荷刷新 → 今日相关洞察按结果刷新 → Coach 追问读到最新标注 → 撤销后三处一致。昨晚训练应刷新受其影响的信息，今日专属的练后提示沿用原定义。另验收多候选、点击前记录变更、退出重开和端侧选中同一对象。
- iPhone 使用可辨认的 Watch 训练做同样流程，核对提交与撤销两次切页结果，再验证手改后的撤销冲突。记录实际部署版本、模型路由与验收结果。

## 后续设计边界

近期闭环通过后，按 [Coach 数据治理与持续跟进设计](coach-data-governance.md) 拆分新的交付场景。

- 餐食若需要按发生时刻分析，在后续工单增加可空进食时刻或区间及来源精度。日结、营养完整度与时间精度继续独立。
- 实现阶段目标与复盘前，先定义指定日期的有效目标选择、临时覆盖到期、历史证据与晚到记录的关系。保留已确认的个人规则和持续跟进体验。
- 当前以现有 ReadModel、TCA 和本地事务做完整闭环。借这些流程的验证结果再判断通用事件总线的必要性。观测预测沿用现行非因果边界。
