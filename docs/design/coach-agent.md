# BodySeek Coach Agent 顶层设计

> 状态：已确认的产品设计，待分阶段实现
> 确认日期：2026-11-21
> 范围：私人健康助手、跨页面数据治理、Ontology、对话操作与持续跟进。
> [PRD](../PRD.md) 定义产品目标和边界。[V5 AI Agent 开发指南](../AI_AGENT_SPEC.md) 记录当前已接通的能力。开发与验收先核对对应的生产入口。

## 1. 产品目标

Coach 是贯穿今日、健身、营养、趋势和聊天的私人健康助手。它主动调用相关记忆，结合近期证据和个人基线分析变化，在获得授权后更新真实数据，并把用户交办的事情跟到有结果。

用户应能在三个场景感受到这项能力。

- **看懂变化。** 问「这周恢复为什么下降」，Coach 先验证变化，再比较睡眠、训练、打卡和饮食。结论带日期、依据和覆盖范围，候选解释与已确认事实清楚可辨。
- **接住目标。** 用户说「这两周赶进度，优先睡眠，力量训练保留两次」，后续排训练和复盘会沿用这个阶段的优先级和目标。到期后解除临时约束，使用该日期仍有效的目标和偏好。
- **办完交代的事。** 用户可用聊天记录饮食、补训练标注、修改明确目标或交办跟进。结果进入对应业务页面。Coach 在后续对话和复盘中引用最新记录及操作历史。

目标冲突时，先应用用户已定的阶段优先级和有效约束。有明确取舍时给出选项和代价。若优先级尚未确定且选择会实质影响计划，询问一次，在约定期限内沿用用户决定。

## 2. Ontology 与共享数据

Ontology 是全 App 对健康对象、关系、含义和可执行操作的共同定义。优先扩展 [领域术语表](../../CONTEXT.md)、BodySeekCore 的类型化合同、GRDB 中的业务记录和 `bodyseek-evidence-v1` 工具证据。界面和 Agent 通过相同标识引用对象，由现有本地计算和持久化路径提供事实。

| 对象 | 含义与关键关系 |
| --- | --- |
| 健康信号与记录 | 设备观测、用户记录与估算各带来源。训练、餐食和打卡按生理日归属。训练标注关联到具体训练，饮食估算关联到具体条目和值。 |
| 健康目标 | 用户希望在某一周期达到的结果，包含度量口径、目标值、生效时间和有效期。一次目标改动形成新的有效版本。 |
| 计划与执行 | 每日计划可以服务一个目标。实际训练、餐食或打卡可作为计划执行证据。采纳、完成与未记录分别表示。 |
| 记忆与个人规则 | 用户确认的偏好和约束带来源及适用时间。个人规则由用户命名，使用可核对的条件为记录或日期分类。 |
| 发现、建议和复盘 | 关联观察或建议引用证据窗口、覆盖情况和生成时采用的目标版本。用户的决定和实际结果可追溯。 |
| 跟进任务 | 连接用户问题、目标或个人规则，以及观察时间、触发条件和最后交付的发现或复盘。 |

对象至少可以追溯到稳定标识、来源、归属日期及修订记录。具体值按需保留单位、来源类别、估算标记、算法版本和四态可用性。统一使用本地 04:00 的 `DayKey` 口径。分别记录事实发生时间与应用获知时间，区分目标生效日期和实际修改时刻。

### 2.1 数据治理

Coach 负责发现缺失、重复、冲突和过期约束，根据用户的问题发起证据查询、整理或订正。采集、去重、聚合、评分、动作验权和事务由各自的本地合同执行。保留已有的估算边界、HealthKit 来源与五项评分独立性。

- **归属与去重。** 用户明确指向唯一对象、存在已确认关联，或同一来源命名空间有相同记录 ID 时，可自动关联并保留各自来源。日期、时间、名称相似时给出候选项。Watch 补同步后仍须核对训练只计一次，手动标注可追溯。
- **缺项与冲突。** Coach 可以解释哪天缺了什么、哪些值来自手工或估算，以及会影响哪个结论。缺失和排除保持原状态。跨日覆盖率按请求窗口计算。订正后由同一条派生链更新受影响的页面与汇总。
- **个人规则。** 用户可定义「赶工夜」等概念。Coach 说明分类条件、数据来源、适用时间以及缺测如何处理。条件明确且有数据时创建规则，支持查询、编辑和停用。个人规则有自己的版本和结果，正式健康指标沿用已批准的定义。
- **历史订正。** 最新统计使用订正后的事实。已保存的复盘保留当时可见的证据、目标版本和建议，并提示后续订正及其影响。复盘历史遵循用户的数据保留与删除设置。

例子：手表已经记录昨晚的训练。用户说「昨晚那次是腿训，把这周力量目标改成两次，周六看恢复再决定练不练」。Coach 给唯一匹配的训练追加标注，更新本周目标，把周六记为待决定。健身页和今日页显示各自更新。后续的训练次数按实际训练计算，周六的建议使用当时可获得的恢复和体感证据。

## 3. 对话操作与授权

| 用户意图 | 目标交互 |
| --- | --- |
| 明确、低风险、可撤销的记录或编辑 | 一句话可构成授权。日期、对象和修改内容明确时可直接执行，例如记录下午的咖啡、为明确训练补标注、把本周力量目标从三次改为两次。 |
| 表达想法、询问建议或对象不明确 | 继续讨论，或只问会影响结果的最少信息。诸如「最近太忙，是不是该少练一点」进入协同决策。 |
| Coach 主动建议调整计划、批量删除、连带影响多个目标 | 展示具体改动和影响，等待显式确认。主动建议的计划变更沿用 [ADR 0008](../adr/0008-ai-proposes-user-confirms-plan-changes.md)。 |

对话意图进入类型化操作，由本地检查授权、对象唯一性、范围和业务约束。实际持久化成功后，Coach 回执显示修改对象、日期、结果及适用的撤销入口。估算值照现行规则标明。一次指令含多项操作时，结果逐项可核对。重试使用同一操作标识，避免重复写入。撤销若遇到之后的修改，先展示冲突及可恢复部分。

用户自己下达的明确编辑指令，按授权范围执行。模型从对话中自行提出的长期记忆和计划调整，沿用待确认提案。实施前按 [现行开发指南](../AI_AGENT_SPEC.md) 核对当前确认入口和审计机制。

## 4. 主动记忆、持续任务与主动性

- **记忆。** 提问时主动检索与事项有关且仍有效的用户目标、偏好、限制和过去决定。必要时用一句话说明引用了哪条记忆。明确要求记住的事实可按授权保存。模型观察到的重复现象可带证据供讨论，经确认后才成为长期偏好或已确认规律。用户可纠正、停用和查看应用期限。
- **跟进。** 创建时说明观察对象、所需数据、触发条件、有效期及交付方式。用户随时能查询进展、改期限或叫停。任务按待观察、待用户判断、完成或已停止表达状态。到期回顾实际数据、缺测和建议，说明数据不足的原因并提供下一步。
- **主动出现。** 默认在 App 内呈现与当前决定或已交办任务有关的提醒。用户明确交代跟进并授权推送时，才使用系统通知。相同事件去重。通知及后台能力受系统实际调度约束，App 打开时补检查待处理任务。
- **外部上下文。** 优先使用用户直接提供的日程和约束。未来外部连接按任务单独授权，例如排训练时只读取指定日历的空闲时间。云端模型按当前配置提供能力，传输限本次任务所需的有界证据。原始 HealthKit 样本留在设备。

例子：用户交办「两周后看看晚喝咖啡的日子是否睡得更晚」。Coach 在开始时核对「晚喝」和入睡时间口径。到期给出可用天数、两组观察结果和限制，保留关联的解释边界。如果咖啡时间经常缺失，明确哪些记录影响结论。

## 5. 实施顺序与验收

| 阶段 | 首个完整流程 | 通过条件 |
| --- | --- | --- |
| 1. 证据与身份 | 用同一问题比较最近 7 天与更早 28 天，关联训练、睡眠、体感、饮食和计划执行。 | 日期、来源、覆盖率、已知零与缺失核对正确。Watch 晚同步、明确重复和疑似重复分别有可复核结果。 |
| 2. 对话办事 | 完成「补昨晚腿训标注＋把本周目标改为两次」，再从健身和今日核对，追问后撤销其中一项。 | 明确指令与讨论正确分流。高影响操作要求确认。页面状态、写入回执、重试和撤销一致。 |
| 3. 持续个人助手 | 交办两周咖啡与睡眠观察，中途修改期限或补一条数据，最终在 App 内查看复盘。 | 生效目标、记忆、规则与任务期限一致。重复触发去重。历史复盘能说明生成后发生的订正。 |

开发使用同一组固定样例做前后对照，并从相关 SwiftUI 入口验收真实读写。分别记录云端、端侧、离线与数据不足时的可用能力。线上模型与真机调度单独验证。评价看用户能否更少操作地完成一件事，以及结论、实际变更和跟进结果能否核对。
