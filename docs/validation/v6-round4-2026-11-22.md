## 3. 设计决策

1. **`BodyModelStore` 放在 `BodySeekStore`**。它只依赖 Core 和 GRDB；依赖方向是 Core ← Store ← Health ← Agent ← Features。Features 通过 `BodySeekStoreClient.observeBodyModel` 订阅，不接触 GRDB。放进 `BodySeekFeatures` 会让 Features 直接依赖 GRDB，违反现有分层。
2. **快照只放"动作层会写的业务表"的指纹**，不含 `day_metric` 等健康高频表（那部分仍由 `BodySeekReadModel.observeDashboard` 负责）。指纹字段：记忆数与时间戳和、审计数与最近时间、营养日志数与更新时间、计划项状态摘要、打卡数、简报最近生成时间、训练标注数。`removeDuplicates()` 去重。
3. **AppFeature 的刷新是"增量"的**：第一帧只记基线；记忆变了才改 `tieredMemories`；标注数变了才发 `workout.onAppear`；营养、计划、打卡变了才重新读 supplemental context（`cancelInFlight` 去抖）。旧路径保留：`coach.delegate(.appliedActionsChanged)` 会主动 `loadFitnessStore + loadSupplementalContext`。
4. **没有注入网关时行为完全不变**：`AgentExecutionContext.actionGateway` 默认 `nil`，预览、评测、旧测试依旧只生成确认卡片，所以 Agent 评测 `direct_write_violations=0` 的口径不受影响。
5. **`propose_plan_change` 仍是确认卡片**：`adjustPlan` 在目录里声明 B 级但 `isUndoable == false`，`effectiveRisk` 因此为 C。工具返回里加了 `authorization: "C"`。
6. **撤销复用现有实现**：`undoAction` 对 `annotateWorkout` 直接调用 `undoWorkoutAnnotation`；记忆、营养日志用同一事务内的 before/after 快照 + 冲突检查（当前数据 ≠ after 快照 → `undoConflict`，不写撤销审计）。已撤销再撤销返回原撤销审计（幂等）。
7. **保存记忆的撤销 = 停用**（`retired_at = now`），不物理删除，避免 FTS 触发器和审计引用悬空。保存前就已存在的记忆（覆盖更新）不能自动还原，抛 `undoUnsupported`。
8. **回执存在消息的 `tool_trace_json` 里**（新增可选字段 `appliedActions`），不改表结构。读取时再按审计表补 `undoneAt`，所以撤销后重开 App 状态一致。
9. **Coach 直接执行的标注不走 `coachAnnotationDecision`**：审计 ID 是新 UUID，回执 ID = 审计 ID，撤销用回执 ID。消息上不再设置 `workoutAnnotationProposal`，所以不会同时出现确认卡。
10. **C 级动作的 `delete_meal`**：`execute_action` 只会得到"需要确认"，不会写入；系统提示词要求 Coach 让用户到饮食页自己确认（当前没有对应的确认卡片 UI，列入后续）。
