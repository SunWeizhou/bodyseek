# V6 第三轮：数据层统一（2026-11-22）

> 状态：已实施，**未编译、未测试**。依据：蓝图第 1 阶段、ADR 0021。

## 1. 先核对的事实（与任务描述不一致的地方）

读源码后发现，任务描述的前提已经不成立，所以本轮的范围比原计划小：

- `FitnessStoreClient.liveValue` 的 11 个方法**已经全部读写 GRDB**（经 `BodySeekSharedStore` → `BodySeekRepository`）。训练模板、训练记录、记忆、Coach 消息在 v1 迁移里就有对应的表（`workout_template`、`logged_workout_session`、`memory`、`coach_message`），schema 够用，**不需要新列**。
- SwiftData（`BodySeekSwiftDataBackend`、`Stored*` 四个 `@Model`）现在只做两件事：`exportLegacyPayloadIfStoreExists()`（一次性导入的读取端）和 `deleteLegacyStoreIfExists()`（用户重置时删除旧文件）。
- 一次性导入已存在：`LegacyDataImporter.importIfNeeded`，持久化标记是 `sync_anchor` 里 `legacy_import_v3`，重置后用 `legacy_import_v3_dismissed` 防止重新导入；已有幂等和重置测试。
- 记忆已经统一：GRDB 里只有一张 `memory` 表（`TieredMemoryRecord`），导入时把 `AthleteMemoryItem` 转成 `TieredMemoryRecord`。`AthleteMemoryItem` 现在是 `Repository.loadAthleteMemories/saveAthleteMemory` 上的桥接视图类型，被 `CoachFeature`、`SettingsFeature`、`WorkoutFeature`、`CoachView`、`CoachMemorySheetView`、`CoachToolRegistry`、`MemoryContextSelector` 使用。

**因此本轮没有重写 `FitnessStoreClient`，也没有删除 SwiftData 代码。** 把 UI 层的 `AthleteMemoryItem` 换成 `TieredMemoryRecord` 需要改 7 个 Features / Agent 文件，收益只是类型整洁，风险不小，建议留给第六轮页面迁移时顺带做（见 §5）。
